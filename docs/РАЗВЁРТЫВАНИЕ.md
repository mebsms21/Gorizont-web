# Локальная разработка и публикация на хостинге

## Локальная установка

1. Распакуйте архив проекта. Установите Docker с Compose v2, Bash и OpenSSL.
2. Запустите `./bin/configure.sh`. Он создаст `.env` со случайными паролями. При необходимости измените `WP_PORT` и `WP_URL` согласованно, до установки.
3. Выполните `./bin/setup.sh`. Скрипт поднимает MariaDB и PHP, устанавливает WordPress, включает тему и плагин, добавляет демо и русский язык.
4. Откройте URL из `.env`. Для входа используйте значения `WP_ADMIN_USER` и `WP_ADMIN_PASSWORD` из своего `.env`.

Установщик читает пароль из окружения и не выводит его. Не публикуйте `.env`, архивы базы или файлы локальных томов. Стандартные образцы WordPress удаляются только при первой установке на пустую базу. При обнаружении установленного сайта `setup.sh` завершает работу, сохраняя его настройки.

Для остановки: `docker compose stop`. Для запуска: `docker compose up -d --wait`. Данные хранятся в именованных томах. Исходники темы и плагина подключены из рабочей папки в режиме read-only для контейнера; редактируйте их обычным редактором.

Если русская локализация не скачалась, повторите:

```bash
./bin/wp language core install ru_RU --activate
```

При корпоративном HTTPS-прокси настройте доверие к сертификату вашего прокси. Не отключайте TLS-проверку. В управляемой тестовой среде русский пакет был загружен по HTTPS снаружи контейнера, а доверенный CA добавлен в локальный runtime; сертификаты и ядро runtime не входят в архив проекта.

`compose.nginx.yaml` — дополнительная конфигурация для Nginx + PHP-FPM. Запускается отдельно: `docker compose -f compose.nginx.yaml up -d --wait`; не запускайте её одновременно с основной средой на том же порту и томах. В ней UID PHP-FPM совпадает с CLI (82). Локальный первичный установщик `bin/setup.sh` рассчитан на основной `compose.yaml`. В Nginx-варианте первичную установку можно пройти через браузер, затем активировать тему/плагин и импортировать демо в панели. Этот вариант подготовлен, но полный запуск в данной среде не завершён из-за лимита диска Docker VFS.

## Обычный WordPress-хостинг

Требования: актуальный WordPress (проверено на 7.1.4), PHP 8.2+ (проверено на 8.3.36), MariaDB 10.6+ / MySQL 8+, HTTPS, PHP memory_limit от 256 МБ. Тема использует theme.json v3, поэтому минимальный WordPress — 6.6. На production выбирайте актуальную поддерживаемую версию, а не минимальную.

1. Подготовьте отдельный staging-домен и установите WordPress на русском языке. Включите HTTPS.
2. Создайте резервную копию существующих файлов и базы, если хостинг уже содержит сайт.
3. В «Плагины → Добавить → Загрузить» установите `gorizont-core.zip`, активируйте его.
4. В «Внешний вид → Темы → Добавить → Загрузить» установите `gorizont-theme.zip`, активируйте тему.
5. Для демонстрационного сайта нажмите «ГОРИЗОНТ → Добавить демоматериалы». Для собственного наполнения создавайте страницы и материалы вручную.
6. В «Настройки → Чтение» выберите статическую главную «Главная». В «Постоянные ссылки» выберите «Название записи» и сохраните.
7. В «Настройки → Общие» проверьте название, описание, часовой пояс Москвы и адреса HTTPS. В «Внешний вид → Редактор» проверьте меню и ссылку политики, особенно при установке WordPress в подкаталог.
8. Замените демонстрационные проекты, реквизиты и юридические тексты. Удалите надпись о демоверсии из подвала после подготовки реального содержимого.
9. Включите HTTPS-редирект, серверное кеширование/OPcache и сжатие. Проверьте, что REST API, wp-cron, загрузка файлов и обновления не блокируются хостингом. Кеш исключает `/wp-admin/`, `/wp-login.php`, авторизованных пользователей и должен учитывать query-параметры фильтров.
10. После проверки снимите «Попросить поисковые системы не индексировать сайт». Локальная среда намеренно использует `blog_public=0`. Проверьте `/wp-sitemap.xml`, canonical и отсутствие `noindex` на основных страницах.

WordPress нельзя опубликовать как статический сайт на обычном Vercel-хостинге. Нужны PHP и база данных. Репозиторий не требует Next.js, Node-сборки или платного конструктора для работы.

## Перенос локальных данных

Тема/плагин не содержат содержимое базы. Для переноса всех отредактированных страниц и изображений перенесите базу и `wp-content/uploads/` либо используйте штатный экспорт/импорт WordPress. Дополнительные опции контактов и настройки редактора сайта надёжнее переносить вместе с базой.

```bash
mkdir -p backups
./bin/wp db export - > backups/gorizont.sql
```

Для медиатеки используйте SFTP/архив тома. Не переносите локальный `wp-config.php`, `.gorizont-salts.php` или `.env`: на хостинге должны быть собственные реквизиты БД и ключи.

После импорта на staging выполните WP-CLI на хостинге:

```bash
wp search-replace 'http://localhost:8080' 'https://staging.example.com' --all-tables-with-prefix --skip-columns=guid --precise --dry-run
# Проверьте отчёт, затем повторите без --dry-run.
wp rewrite flush
```

Это корректно обрабатывает сериализованные настройки и ссылки внутри Gutenberg. При последующем переносе со staging на основной домен повторите замену для соответствующих адресов.

## Настройки production и откат

`WP_DEBUG=false`, `WP_DEBUG_DISPLAY=false`, `DISALLOW_FILE_EDIT=true`, `WP_ENVIRONMENT_TYPE=production`. Уникальные пароли, минимальные роли, двухфакторная авторизация администратора средствами хостинга или проверенного плагина. Настройте автоматические резервные копии базы и uploads и проверьте восстановление. Права файлов обычно 644, каталогов 755; не используйте 777. Закройте доступ к конфигурации, логам, архивам и выполнение PHP в uploads средствами веб-сервера.

До смены домена сохраните резервную копию и согласуйте окно переключения. При ошибках восстановите предыдущие файлы и базу из одной согласованной точки. Активация другой темы не удаляет услуги, проекты и контакты; оставьте `gorizont-core` активным.

Формы заявок, CRM, аналитика и SMTP не подключены: в текущем задании они не определены. Кнопки ведут на страницу контактов. При добавлении этих функций потребуется настроить реальную доставку, антиспам и актуализировать политику обработки данных.
